# 006 バージョンの確認とアプリの入れ替え

配布した zip から入れたアプリを、利用者の確認後に同じフォルダで更新する。既存のマウントの停止手順と登録先を保つ。

## バージョン

バージョンは Directory.Build.props の Version で定義する。画面と通常の CLI は major.minor.patch のみを表示し、コミットの印は version --json の result.commit に分ける。
比較するのは三つの整数。v0.1.0 の形のタグを使い、形の合わないタグと先行版は更新候補にしない。

## 配布単位

DbxLight-<version>-win-x64.zip と同名の .sha256 を使う。ハッシュの行は小文字の SHA-256、空白二つ、zip の名前。
zip は平らなファイルだけを持ち、常駐と CLI の exe・dll・runtimeconfig.json・deps.json、共有の Core.dll、release.json を含む。指定された場合だけ LICENSE を含める。PDB は含めない。
.NET 8 デスクトップ ランタイム、rclone、WinFsp は利用する PC に別途必要。常駐の GC と TieredCompilation の設定は publish の出力に引き継ぐ。
release.json は schema=1、version、名前順の files（name・size・sha256）を持ち、自身は一覧に含めない。

## 作成ツール

tools/make_release.py は Python 3.12 の標準ライブラリだけを使う。source と out を指定し、license と試験用の version を追加指定できる。
二つのプロジェクトを Release・win-x64・ランタイム別置きで同じフォルダへ publish する。-m:1 と --disable-build-servers を付ける。
DebugType=None と DebugSymbols=false で PDB を生成せず、PathMap でビルド元の絶対パスを固定の仮想パスへ写す。
ユーザー名とホームの両区切り表記を UTF-8・UTF-16LE で走査する。検出時は名前とバイト位置だけを出し、zip とハッシュを作らず終了値1。
名前順、固定時刻、固定の圧縮設定で同じ入力から同じ zip を作る。空でない出力先には何も書かず終了値2。引数の誤りは終了値3。
復元は空のローカルのパッケージ供給元を使う。外部パッケージを追加しない。配布用の zip は、ソースと一緒に公開されている tools/make_release.py で作る。

## 確認先

公開先の指定は UpdateSource の定数一つから組み立てる。このリポジトリの Releases の latest API を匿名 GET で読む。
API の Accept は application/vnd.github+json、zip と .sha256 は転送後も application/octet-stream。アプリのバージョンを含む User-Agent を送り、ETag があれば If-None-Match を送る。304 は保存済みの候補を使う。
API と .sha256 は各30秒、zip は API の size により30秒 + 1 MiBあたり10秒を要求の開始から本文の読了までの上限にする。資産 URL は ASCII だけを受け付け、利用者名とリポジトリ名の部分だけ大文字と小文字を区別しない。
API の tag_name・draft・prerelease と、資産の name・browser_download_url・size・digest を読む。下書きと先行版を対象にしない。
404、403、時間切れ、不正な JSON、必要な資産の不足は確認失敗。認証情報やトークンを読む・保存する・送る処理は持たない。
本物の通信は HTTPS に限り、転送は5回まで。転送先も HTTPS。最初の資産 URL は、このリポジトリの Releases の download パスに限る。
DBXL_UPDATE_FEED は明示のポートと末尾の / を持つ http://127.0.0.1:<port>/ または http://localhost:<port>/ で始まる場合だけ有効。試験の API はその下の releases/latest、資産も同じホストとポートを使う。それ以外の指定は無視する。

## 通信するプロセス

確認とダウンロードと展開は dbxl.exe が行う。常駐は隣の CLI の JSON を読む。HTTP 通信の処理を常駐で作らず、定期的な通信のためのメモリを常駐へ持たせない。
CLI が隣にない場合、自動確認を省略し、手動確認では zip から入れ直す案内を出す。

## 検証

入れ替える前に、次を確認する。

- 必須の .sha256 と zip の SHA-256 が一致する。API の digest があれば、それも照合する。
- zip は50 MiB以下で API の size と実際の大きさが一致する。
- 名前は平らなファイル名だけ。区切り、..、絶対パス、ドライブ文字、コロン、予約名、末尾の空白・点、重複、リンクを拒否する。64件以下、展開後の合計100 MiB以下。全件を調べてから展開する。
- release.json の schema と版を確認し、全ファイルの大きさと SHA-256 を照合する。掲載のないファイルは拒否し、両方の exe を必須とする。
- ネットワークからの取得は実行中の版より新しい場合だけ。ローカルの --from は旧版へ戻すためにも使える。

.sha256 は破損の検出に使う。配布元そのものが書き換えられ、zip とハッシュの両方が置き換わった場合は防げない。実行ファイルへの署名と署名の検証はない。

## 置き方

実行ファイルと同じフォルダに release.json と掲載された全ファイルがあり、フォルダへ書き込める場合だけ自動で入れ替える。
開発のビルド出力、CLI と常駐が別の場所にある場合、書き込めない場所では確認までとし、Releases の zip を展開し直す案内を出す。管理者へ昇格しない。
入れ替え時には元のファイルのハッシュも照合し、登録外の同名ファイルの上書きとリンクを拒否する。

## 入れ替えと戻し

取得したファイルは状態ファイルの親の update/staging-<version>-<乱数> に置く。
常駐は既存の「終了」と同じ通常停止を使う。アップロード待ちでは待機でき、取消しと停止失敗では更新予約も取り消す。更新時は強制停止を選べない。
監視中からの更新は、自分の生きた監視・世代・子プロセスを照合し、通常停止の Clean と、回復不要・停止完了の記録を同じ ControlGate 内で確認する。監視終了や別プロセスの動作、停止後の記録の変化では更新予約を取り消し、停止済みに留めて更新を始めなかった理由と再開の手順を通知する。別プロセスの動作の通知とステータス画面の表示も保つ。強制停止、Windows 終了、Dispose では予約を取り消すだけにする。
停止済みからは、自分の一時停止の受領を条件にしない。同じ設定の Clean な停止記録があり、その記録のプロセスが終了済みである場合、または記録が一つもない場合に更新できる。ダウンロード前と最終停止時に ControlGate 内で確認し、不明ならダウンロードせず、停止済みに留めて通知する。
アップロード待ちの間に rclone が終了しても、監視が起動し直した後の通常停止がきれいに終われば更新する。最後の停止記録で安全を確認する。
照合後、終了直前に staging の新しい CLI を DetachedProcess で切り離して起動する。自動起動の登録と共通の関数で、絶対パスの config・state と試験用の登録先だけを組み立て、区切りの -- の後ろへ渡す。1回きりの操作は渡さない。
swap を起動できない場合は更新予約を取り消し、常駐を停止済みで残して、メニューからの再開を案内する。

swap は置き方と staging を再検証し、指定 PID と起動時刻が一致するプロセスの終了を120秒まで待つ。起動時刻が違う場合は、元のプロセスは終了済みとして扱う。旧版と新版の対象ファイル全部の排他を確認してから移動を始める。
旧ファイルは backup/<旧版>-<UTC時刻> に移し、新ファイルを置いて再照合する。元のファイルは読み書きを共有しないハンドルで保持し、移動だけを許す。
新しいファイルは CreateNew で開き、作成できた時点で戻しの対象に記録する。新版の照合には、最初に検証した manifest とそのバイト列を保持して使う。戻しの照合には、移動前の旧 manifest とそのバイト列を使う。
途中の失敗では自分で作ったファイルを除き、移した旧ファイルを戻して、旧 manifest と照合してから旧常駐を起こす。戻せた場合はその回に作った空の backup フォルダを除き、結果の backupPath を null にする。復元にも失敗した場合は起動せず、結果に backup の場所を残す。
どちらの manifest にもないファイルとフォルダ、既存の自動起動・右クリック・左の一覧の登録には触れない。
結果は update/last-result.json。失敗の段を stage に残し、例外の reason は記録用に保つ。起動した常駐は段ごとの案内を一度通知し、読んだ印を保存する。backup の場所を通知するのは戻しに失敗した場合だけ。
完了した staging は外側の記録と排他ファイルで識別する。未完了でも最後の書込みから7日以上なら片づける。稼働中の swap は片づけない。backup は名前の形、読める manifest、全掲載ファイルの存在を確認し、完全な物の新しい二つを残す。不完全な物と壊れた物は枠に数えず保全する。名前の合う空の物は除く。リンクや壊れた項目は飛ばし、ほかの片づけを続ける。リンクをたどらない。

## CLI

CLI は version と --version、update check、update download、update apply を受け付ける。成功 JSON は ok と result、失敗は既存の code と message を使う。
--yes がない apply は操作の案内だけ。--from は通信せず、--sha256 があればローカル zip と比べる。常駐または対象の状態にマウントが残る場合は断る。
実行中の CLI 自身も旧ファイルを使っているため、apply は新 CLI へ入れ替えを予約して終了する。終了値0と scheduled=true は予約の成功であり、完了は resultPath の success で確認する。
update swap は内部用。通常の利用では直接呼ばない。AI ツールは update check --json で確認し、入れ替えは人が決める。

## 常駐

メニューの「ログインと接続先」の下に「更新を確認」を表示し、候補を知っている間は「バージョン <版> に更新」を表示する。
設定には現在の版と「新しいバージョンを自動で確認する」を表示する。updateCheck の既定は true。古い設定に項目がなくても読める。
起動の2分後と、前回の試行の24時間後のうち遅い時刻に確認する。手動はこの制限を受けず、既知の更新も毎回通知する。
確認時刻、ETag、候補、通知済みの版を update/check.json に保存する。自動確認では実際に通知できた場合だけ通知済みにし、版が一度戻っても同じ版の通知を繰り返さない。updateCheck だけの保存はマウントを止めず、タイマーを再設定する。自動確認の失敗は通知せず、次の回へ回す。
更新のための停止も、通常の停止が持つ未アップロード・不明なファイルの保護を通す。状態を確認できず更新を始めない場合と、swap を起動できない場合は、停止済みでメニューから再開できる。

## 対象外

利用者の操作なしの自動入れ替え、差分更新、署名、インストーラー、rclone と WinFsp の更新、認証やプロキシの設定、先行版のチャンネル、GitHub Actions は作らない。
アプリはタグや Releases の作成、ソースの公開操作を行わない。

## 残る制約

電源断や OS の停止による途中終了は、実行中のプログラム内で戻せない場合がある。backup の原本と最後の記録を保って、手で戻す。
ウイルス対策などにより置いた exe が起動できない場合、同じ場所のファイルと結果を確認し、必要なら旧 zip を展開し直す。
.NET ランタイムがない PC では CLI と常駐を起動できないため、更新機能も使えない。
異なる状態ファイルを使う常駐が同じ置き場で動いている場合は、ファイルの排他で入れ替えを断る。CLI は --state で選んだマウントを確認する。
完全な backup 二つと、不完全な backup・新しい未完了の staging は容量を使う。稼働中の staging は保全し、次の起動で片づけの条件を判定する。
DBXL_UPDATE_FEED は配布用の実行ファイルでも読まれる。接続先はこの PC 内の loopback に限る。同じ利用者はアプリの置き場へも書けるため、新しい権限の入口にはならない。
置き場が変わっていない検証・置き場の確認 (target)・待機・排他の失敗では、結果を書いた後に旧常駐を起こし直す。結果の保存が失敗しても起こし直す。戻しの失敗時だけ自動で起こさない。
監視中からの更新は通常停止が Clean で完了した場合だけ実行する。停止済みでは同じ設定の Clean な停止記録とプロセスの終了、または記録が一つもないことを確認する。確認できない場合は更新予約を取り消し、常駐を停止済みで残して通知する。
更新時の停止は照合と停止を同じ排他内に保つため、別プロセスが起動準備中に ControlGate を保持している間は待機し、上限に達すると「停止できません」を表示する。
同じ利用者の別プロセスによる悪意のある書き換えや、電源断を含む永続的なトランザクションの保証は対象にしない。
